# Obsidian OS — the encrypted install path (task 1.5)

Design note for `debos/installer/`. It records the install chain as designed,
what is a Calamares module config, what is still missing code, and what has not
been tested. The configs themselves are in `debos/installer/`; the file-by-file
notes are in [`../debos/installer/README.md`](../debos/installer/README.md).

**Status: a design, not a feature.** No Calamares run, no disk written, no
reboot into an installed Obsidian OS. Section 5 is the honest version of what
that means.

## 1. The chain

```
                     ┌─ view phase ─────────────────────────────────────┐
  welcome  locale  keyboard  partition(Erase, LUKS2 pre-checked)  users  summary
                     └──────────────────────┬─────────────────────────────┘
                                            │ user confirms
                     ┌─ exec phase ─────────▼─────────────────────────────┐
  partition   GPT: 512 MiB ESP (fat32, /boot/efi)
                        + LUKS2 #1  25%  -> /
                        + LUKS2 #2  30%  -> /home
                        + LUKS2 #3  45%  -> /var/lib/libvirt
  mount       target mounted; ESP bind-mounted at its mount point
  unpackfs    /run/live/medium/live/filesystem.squashfs -> target root
  fstab       /etc/fstab + /etc/crypttab (luks,keyscript=/bin/cat)
  users       one sudoer, "obsidian", 0700 home, no root password
  initramfs   rebuilt, now carrying the LUKS keyslot data
  grubcfg     /etc/default/grub; GRUB_ENABLE_CRYPTODISK=yes (computed)
  bootloader  grub-install on the disk holding the ESP
              + rd.luks.uuid=luks-<uuid>  (or cryptdevice=…; see gap 1)
              + root=/dev/mapper/<luksMapperName>
  umount      -> finished -> reboot
                     └──────────────────────────────────────────────────┘
```

Three separate containers, not one, matches `docs/ARCHITECTURE.md` §2: `/`,
`/home` and `/var/lib/libvirt` each in their own LUKS2 container, Argon2id,
XTS-AES. The ESP is necessarily unencrypted — FAT cannot be a LUKS container,
and GRUB needs to read it — and the partition module is left with
`showNotEncryptedBootMessage: true` so the installer says so out loud rather
than leaving it to a later audit.

Swap is not on disk. `userSwapChoices: [none]`; the image uses encrypted zram
at runtime, so there is no encrypted swap partition to configure, which is also
why `luksopenswaphookcfg` is not in the sequence.

### Where the LUKS details come from

| Property | Set by | Key |
|---|---|---|
| container format | partition module | `luksGeneration: luks2` |
| encryption offered/pre-checked | partition module | `enableLuksAutomatedPartitioning`, `preCheckEncryption` |
| filesystem inside the container | partition module | `luksFileSystemType: ext4` |
| passphrase keyslot KDF | cryptsetup's LUKS2 default (argon2id) | *not configurable here* |
| key-file keyslot KDF | luksbootkeyfile module | `luks2Hash: argon2id` — module off by default |
| mapper name / uuid | generated by the module, published to global storage as `luksMapperName` / `luksUuid` | *not settable* |
| unlock at boot, GRUB | grubcfg module | `GRUB_ENABLE_CRYPTODISK`, computed |
| unlock at boot, kernel | bootloader module | `rd.luks.uuid=` / `cryptdevice=` + `root=/dev/mapper/…` |
| unlock at boot, initramfs | fstab module | `crypttabOptions: luks,keyscript=/bin/cat` |
| TPM2 auto-unlock | nothing yet | `scripts/boot-keys.sh tpm` — gap 3 |

Upstream's own note on this is worth repeating because it is the whole
difficulty: `luksGeneration` defaults to `luks1` upstream precisely because
"grub doesn't support LUKS2 + Argon2id currently". LUKS2 + Argon2id is safe
here **only because the passphrase is not typed into GRUB** — the initramfs
opens the container. If GRUB's cryptodisk ever becomes the thing that unlocks
root, the KDF has to drop to PBKDF2 or the machine does not boot. That coupling
is a comment in `partition.conf` and a line in `grubcfg.conf`'s absence, and it
should stay a comment someone reads before changing either file.

Upstream's guidance for integrators shipping LUKS with GRUB2 and an initramfs
is at the wiki page it links from its own `partition.conf`:
<https://github.com/calamares/calamares/wiki/Deploy-LUKS>

## 2. Config vs. missing code

Config that exists in `debos/installer/`:

- `settings.conf` — view order, exec order, the `partition@plain` instance.
- `partition.conf` — the encrypted default layout; `partition-plain.conf` — the
  same layout with `noEncrypt: true`.
- `unpackfs.conf`, `fstab.conf`, `grubcfg.conf`, `luksbootkeyfile.conf`,
  `bootloader.conf`, `users.conf`.

Missing module configs, in the order the sequence reaches them: `mount`,
`welcome`, `locale`, `keyboard`, `machineid`, `localecfg`, `initcpiocfg`,
`initcpio`, `displaymanager`, `networkcfg`, `hwclock`, `services-systemd`,
`initramfs`, `umount`, `summary`, `finished`. A module with no config file
does not load, so the sequence as written **cannot run end to end** — this is a
missing-file problem, not a design problem, and it is the cheapest thing on
this list to fix.

Missing code, in the order the install reaches it:

1. **The installer is not in the image.** `build/flavors/common.pkgs` has
   `initramfs-tools`, `live-boot`, `squashfs-tools` and none of `calamares`,
   `cryptsetup`, `dosfstools`, `efibootmgr`, `grub-efi-amd64-bin`, `sbctl`.
   There is no `obsidian-installer` entry in `scripts/scaffold-packages.py`'s
   `PACKAGES` table and no `debos/packages/obsidian-installer/`. The 1.4 README
   claimed otherwise; it was wrong.
2. **The configs are not copied to `/etc/calamares/`.** `debos/overlays-src/`
   does not exist. Today the only way these files reach an image is a manual
   copy, and the build's overlay mechanism is `overlays/<flavor>/` under
   `build/build-iso.sh`.
3. **No boot-menu entry.** The "Install Obsidian OS" item next to the live
   session is not in the GRUB config `build/build-iso.sh` generates.
4. **No branding component.** `branding: default` renders upstream's sample
   branding. Obsidian OS needs its own `branding.desc` (product name, image,
   and the QML slideshow the exec pages use).
5. **No post-install exec step.** Secure Boot keys, UKI signing, TPM2
   enrollment and the hostname/user finalize step
   (`scripts/boot-keys.sh enroll|sign|tpm`, `scripts/finalize.sh obsidian`)
   have no invoker. `shellprocess` is the real upstream module for this; its
   config keys were not verified here, so no instance was written rather than
   guessed.
6. **No post-install profile/apply step.** `scripts/finalize.sh` is what
   randomizes the hostname and creates the firstboot marker
   (`touch /etc/obsidian/firstboot`) that the wizard keys off.

## 3. Deliberate decisions, and what they cost

- **Passphrase-only by default.** `luksbootkeyfile` is left out of the exec
  phase. A key file in the initramfs opens the volumes without the passphrase,
  which on a hardened image is a downgrade unless the key is itself sealed.
  TPM2 sealing (`systemd-cryptenroll`) is the intended replacement and is gap 3.
  Cost: every boot prompts for a passphrase until gap 3 lands.
- **UEFI only.** `requiredPartitionTableType: gpt`, no BIOS GRUB, no hybrid
  layout. A LUKS2 + Secure Boot image that also has to work on legacy BIOS
  firmware is a much larger validation surface.
- **`efiBootloaderId: "debian"`.** Upstream is explicit that trixie derivatives
  using unmodified GRUB EFI packages must set this to `debian`, because
  `grubx64.efi` hard-codes that directory name. Cost: the boot entry is not
  branded "Obsidian OS" until the packaging is changed (gap 2).
- **The wizard and the installer create the same account.** `users.conf`
  defaults (`obsidian` / `Obsidian User`) and group list mirror
  `scripts/firstboot-wizard` and `scripts/finalize.sh` exactly, including
  dropping `realtime`, which no Debian package creates and whose absence would
  abort the install via `must_exist`.
- **A known, unresolved conflict.** `scripts/finalize.sh` runs
  `hostnamectl set-hostname "$HF-<4 hex>"`, and in this exec order it runs after
  the users module, so the randomized hostname wins over the
  `hostname.location: EtcFile` write. That is the behaviour Obsidian wants
  (ARCHITECTURE.md §6), so it is left visible rather than papered over, but one
  of the two writers should eventually go away.

## 4. Gaps

1. **Does the installed system boot at all?** (highest risk)
   The bootloader module picks its LUKS kernel arguments by a heuristic: it
   emits `rd.luks.uuid=<uuid>` only if the target has dracut or an
   `mkinitcpio.conf` with systemd in `HOOKS`, and otherwise emits
   `cryptdevice=UUID=<uuid>:<mapper>`. Debian trixie has initramfs-tools and
   neither of those, so the `cryptdevice=` branch is what this configuration
   gets. Whether Debian's initramfs-tools `cryptroot` hook acts on
   `cryptdevice=` was **not verified** — it is upstream's code path for OpenRC
   and mkinitcpio systems, and initramfs-tools is a third thing. The fallback is
   `/etc/crypttab` plus the `cryptroot` hook resolving root itself, which
   `fstab.conf` is configured for, but "should work" is not "works". First
   thing to check on a real install, with `lsinitramfs | grep crypt` and the
   boot log.
   Related: `GRUB_ENABLE_CRYPTODISK=yes` with an Argon2id container. If GRUB
   ever gets to the container before the initramfs does, it cannot open it.
2. **Bootloader branding / NVRAM.** `efiBootloaderId: "debian"` and
   `installEFIFallback: true` are the conservative pair. Whether the firmware
   produces a usable NVRAM entry, and what it is named, needs a real machine
   (and `shim` for Secure Boot — this is task 1.6).
3. **Post-install chain not invoked.** `scripts/boot-keys.sh enroll|sign|tpm`
   and `finalize.sh` are never called, so Secure Boot, UKI signing, TPM2
   auto-unlock, hostname rotation and the firstboot marker do not happen on an
   installed system.
4. **Hardened mount options are not expressed.** `noatime` on `/` and `/home`
   and `nodev` on `/var/lib/libvirt` were asked for in the 1.4 skeleton through
   a `mountOptions:` list that is not a key of the partition module, and the
   `partitionLayout` entry has no options field. The one real place is
   `extraMounts` in `mount.conf` (extra mounts only) and `tmpOptions` in
   `fstab.conf` (`/tmp` only, and that one is configured). Nothing sets them for
   the three real containers.
5. **No runtime choice between the two layouts.** `partition@plain` exists and
   is a real instance, but the only way to select it is editing
   `settings.conf`. The upstream mechanism for offering both is
   `packagechooser` + `packagechooserq`, which is not wired.

Smaller things recorded in the configs themselves rather than here: the
semantics of `luksFileSystemType` (the key is real, read in
`Config.cpp`/`Config.h`, but the shipped `partition.conf` does not document it),
and the interpretation of a trailing `100%` in `partitionLayout` (avoided by
using percentages that sum to 100).

## 5. Not validated on real hardware

Nothing here has been executed. Specifically, none of the following has
happened:

- Calamares has never parsed these files. The keys were checked one at a time
  against upstream sources, which catches misspelled and wrong-shaped keys —
  and did catch thirteen of them — but it does not catch a config that parses
  and installs the wrong thing.
- No disk has been partitioned, no LUKS container created, no `cryptsetup
  format` run, no keyslot written, no initramfs rebuilt.
- No installed system has been booted, so **gap 1 is entirely open**: the
  passphrase prompt, the unlock, the three mounts, the fstab/crypttab entries
  and the GRUB menu entry are all expectations, not observations.
- No VM, no KVM, no QEMU install run. The existing QEMU boot test
  (`tests/boottest.sh`) tests the live ISO and would not notice any of this.
- The Secure Boot, UKI and TPM2 claims in this document rest on reading
  `scripts/boot-keys.sh` and the Architecture spec, not on an enrollment.
  `scripts/boot-keys.sh` itself is unwired into the image (PLAN 1.6, not
  started).

The minimum run that would start retiring this section: boot the live ISO
under QEMU with a second disk attached, install with the default (encrypted)
layout, reboot natively from the target disk, and confirm the LUKS prompt, the
unlock, and `findmnt` showing all three containers from their own devices.
Only after that is a hardware run worth anything, and only after that does
"encrypted install path" describe a thing that exists.
